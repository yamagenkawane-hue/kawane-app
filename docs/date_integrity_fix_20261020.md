# 実績日・予測日整合性の修正

## 要件と設計
- 不明な実績日を今日や予測日で補わない。完了数量と完了日の有無を分離する。
- 完了日不明の工程は完了を維持し、Geminiに残作業として送らない。
- 不明な前工程の日付で後工程を推測しない。後工程自身に実績・開始予定があれば再開できる。
- 社内工程は記録された実績日の数量から日産量を集計する。データ作成日を作業開始日として扱わない。作業時間と待ち時間を復元できない過去データから期間を捏造しない。
- 外注のみ出し日〜戻り日の暦日を使用する。不正・逆転した日付は除外する。
- 保存済み予測に日付計算バージョンを付け、旧版を画面に採用しない。予測不能も最新結果へ反映する。
- 工程移動・梱包完了では実際の作業日を必須入力する。SQLの変更は新規migrationとして用意し、既存データは変更しない。
- 手動更新ボタンを維持し、CSV取込は保留する。

## 検証方針
日付欠損、部分実績、旧予測、後日登録、逆転日付、履歴不足、会社休日・出勤日、完了工程の再予測防止を検証する。

## 運用上の制約
過去の誤登録日の自動補正は行わない。真の作業日を確認して修正する必要がある。
本番DBのmigration適用と既存データの妥当性は、ローカルのテストとは別に確認する。

## 実装結果
- `processActuals`で実績数量・日付を共通判定。日付のない完了と部分実績を区別した。
- 工程表は空の日付を許容し、完了日未登録／予測日未確定を表示する。
- 進捗一覧の移動・梱包完了日は履歴の登録日時ではなく、紐づく生産実績日を表示する。実績取得はページングする。
- 社内工程のGemini入力は実績日ごとの日産量と営業日単位、外注は出し日〜戻り日の暦日単位に統一した。
- 旧版や数量・実績日の変わった保存済み予測は採用しない。予測不能も最新結果へ保存する。
- 工程移動に作業日入力とDB検証を追加。過去日を後から登録しても、工程の最終実績日を過去へ戻さない。

## 検証結果
- AI・日付・工程表の回帰テスト：28件成功。
- 一時的なPostgreSQL（PGlite）で新migrationを実行：11項目成功。
  - 未来日・未指定日・前工程より前の日付を拒否し、数量が変わらない。
  - 作業日と登録日時を分離し、同一要求を再送しても重複しない。
  - 次工程への数量移動、梱包完了・数量補正・在庫反映、日付順と異なる登録を確認。
- TypeScript型チェックと変更対象ESLint：成功。
- Next.js本番ビルド：成功。制限環境ではフォント取得が進まなかったため、ネットワーク利用可能な環境で再実行した。
- 検証DBはメモリー内のみ。実データ・本番DB・Geminiへの送信なし。

## 反映手順
1. `20261020_process_transfer_actual_date.sql`を適用する（旧クライアント向けの5引数RPCは互換維持）。
2. アプリを反映する。
3. 手動更新で新方式の予測を作成する。反映直後の旧予測は未確定として表示される。
4. 過去の誤登録日は元資料を確認して修正する。不明な日は未登録のまま扱う。
