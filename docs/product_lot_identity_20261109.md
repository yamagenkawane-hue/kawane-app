# 製品が異なる同一ロットNoの登録（2026-11-09）

## 要件・設計

- 製品が異なる場合、製造実績登録で同じロットNoを使用できること。
- 工程数量、材料ロット、在庫、出荷・取消、引当履歴、履歴退避を混在させないこと。
- 製品は製品マスタID、製造ロットは内部UUIDで識別する。表示名・ロットNoのみで他製品へ関連付けない。
- 同じ注番・同じロットNo・同じ材料ロットNoの追加実績は、既存のロットへ加算する既存仕様を維持する。
- 注番または材料ロットが異なれば、同じ番号・同じ製品でも別の内部ロットとして管理する。数量・履歴を勝手に統合しない。
- 過去データの自動修復、業務データの削除・再登録は行わない。

## 原因・修正

| 原因／影響 | 修正 |
| --- | --- |
| `lots_lot_no_key` による全製品共通の一意制約 | 古い一意制約を解除。既存の注番＋ロットNo＋材料ロットNoの一意制約は保持 |
| 在庫の「製品名＋ロットNo」制約が、別IDの同名製品や材料違いロットを妨げる | 紐付き在庫は内部ロットIDで一意にする。未紐付けの旧在庫は製品ID・製品番号・名称の順で区別する一意制約 |
| 注番のないロットに重複制約がなくなる | 製品識別子＋ロットNo＋材料ロットNoの一意インデックスを追加 |
| 予定選択で `同じ注番 OR 同じロットNo` の先頭を使う | 注番IDを優先し、旧データは一意な注番でのみ解決。製品不一致や曖昧なデータは選択しない。サーバーでも予定・工程・注番の一致を検証 |
| 実績一覧が予定のロットNoを表示 | 実績ビューに内部ロットIDを末尾追加し、実績に紐付くロットの番号を表示。未紐付けの実績は「-」 |
| ロット詳細が同番号の他製品の出荷・引当履歴を取得 | 内部IDで照合。未紐付けの旧履歴は、同じ注番に同じ番号のロットが1つの場合のみ補完。ロット番号をPostgRESTのOR式へ埋め込まない |
| 履歴退避で同番号の他製品の在庫まで残数・保護対象になる | 内部ロットIDを優先し、未紐付けの旧在庫のみ製品と番号で保守的に照合。退避済みの元の在庫を別ロットへ付け替える操作も保護 |
| 旧減算RPCが同じ製品番号・ロットNoの全行を更新する | 対象が1件の場合だけ処理。複数なら無変更で停止。数量・引当可能数も検証 |
| 旧出荷取消が同じ注番・番号の複数ロットから最新行を推測する | 内部IDを優先。内部IDのない旧出荷や旧引当の復元先が曖昧なら無変更で停止 |
| 在庫マスタから紐付き在庫を別製品・番号に変更できる | ロット情報と不一致になる編集をDBトリガーで拒否 |
| 実績確定後、製造予定の別リクエストだけ失敗すると再登録される | 実績・ロット・予定更新を単一RPCトランザクションへ統合。通信失敗時は同じ入力の再送キーを維持し、DB側も入力内容を照合 |
| 過去日付の追加で工程の完了日が古くなる | 既存完了日と登録日の遅い方を保持 |

製造ロットを指定しない旧梱包登録は、番号だけで在庫を推測せず、ロット選択を求める。計量登録でのロット未指定は維持する。

旧履歴の内部ロットIDがなく、同じ注番に同番号の材料違いロットが複数ある場合は推測しない。該当履歴のロット別表示や旧出荷取消には、管理者による元データの確認・関連付けが必要。

同じ番号の行が作成された後、古い全製品共通の一意制約を単純に戻すことはできない。問題発生時も業務データを削除してロールバックせず、内部IDを維持して追加修正する。

以前のテスト報告F1〜F7全体を本変更で解決したとは扱わない。今回の一括登録・入力照合・完了日維持に関する検証は上記の範囲に限る。
