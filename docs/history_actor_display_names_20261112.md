# ユーザー表示名と注番・ロット履歴の操作者

## 要件・設計

ユーザー管理でログインIDとは別に表示名を登録し、注番・ロット履歴の「操作者」に表示する。未登録時はログインID、特定できない過去の履歴は「不明」、サービスによる自動処理は「システム」と表示する。

操作者は本文のユーザーID・入力された名前ではなく、DBの認証済みユーザーIDとプロフィールから取得する。操作時点のユーザーIDと表示名を非公開テーブルへ保存し、プロフィールの改名だけでは過去の記録を変えない。製造登録に伴う自動移動も、同じ操作をしたログインユーザーで記録する。

## 実装

- `app_profiles.display_name`：最大100文字、任意登録。既存ID・パスワードは変更しない。
- ユーザー管理：一覧・編集に表示名を追加。ログイン中の管理者自身も表示名だけを編集可能。自身の無効化・管理者解除の保護を維持する。
- 新規ユーザー登録にも表示名を追加。未入力時はログインIDを使う。
- ユーザー管理APIは表示名を返すが、内部メールやパスワードは返さない。表示名登録・変更は管理者APIのみ。認証プロフィールは従来のID・権限情報に限定し、ログイン判定を表示名列から切り離す。
- 注番・ロット履歴に「操作者」列を追加し、列が増えた場合は表を横スクロール可能にする。
- DBトリガーは実績・工程移動・在庫・引当・出荷・工程外注日程・外注分割日程・ロット情報の8テーブルを対象にする。
- 実績の登録・修正はその履歴行の操作者、在庫は表示されている現在値を変更した人、引当は登録した人を記録する。出荷登録者と取消者は別々に保存し、取消済み行は取消者を表示する。外注の日程は出し日・予定日・戻り日ごとに保存する。
- プロフィール改名では履歴表示名を変えない。元の実績や日程を後で修正したときは、その修正者で当該表示イベントの記録を更新する。
- 既存工程移動の`created_by`で本人を特定できる場合は、そのIDの現在の表示名（未設定ならログインID）を取得する。過去の操作時点の表示名は推測しない。記録されていない他の過去実績へ現在の利用者を割り当てない。

## 権限と退避・復元

操作者記録テーブルは`app_private`内でRLS有効、全クライアントの直接読取・更新を禁止する。履歴画面は認可付きRPCで対象ロット・受注の表示用名前だけを取得する。別ユーザーのプロフィール一覧・内部メールを公開しない。無効・失効セッションからのRPCは拒否する。

履歴退避ファイルは既存のversion 1形式に任意の`history_actors`を追加して操作者情報を含める。情報がない古い退避ファイルでは新しいキーを付けず、既存のハッシュと形式を維持する。元の履歴管理関数の互換処理を内部の補助関数として保持し、認可・退避照合・削除前の復元検証は既存処理を使用する。

復元中はクライアントが作れない非公開のトランザクション記録を使い、復元実行者を旧実績の操作者として自動記録しない。保存されていた操作者情報を戻す。古いファイルに操作者がなければ不明のままとする。詳細履歴を削除したときは対応する操作者記録も削除し、退避ファイルから復元できる。残る基本情報に対応する操作者記録は維持する。
