## 2. 設計見直し結果

### 2.1 全体方針

要件定義、システム設計書、DBマイグレーション設計書の大きな方向性は一致している。

- 進捗管理は工程別累計ではなく、ロット別の現在位置と数量を表示する。
- 製造工程でロットを確定する。
- 実績登録完了時に、生産数量のみを次工程へ自動移動する。
- 今日生産したロットと翌日生産したロットは別々に移動し、画面上も別々に表示する。
- 元工程に表示対象数量がない場合は `-` を表示する。
- 計量登録、計量表出力は通常運用から廃止する。
- 超過生産は在庫として扱い、引当可能にする。
- 引当と出荷は受注数量を上限にする。

### 2.2 DB設計

DB設計として、ロット別の現在位置を持つ `process_lot_positions` と、工程移動・直接編集履歴を持つ `process_lot_movements` を追加する方針は妥当。

既存の `order_processes.completed_amount` は累計実績としての性格が強く、ロット別の現在位置を正確に表現できない。  
そのため、進捗管理の新表示は `process_lot_positions` を主として参照し、`production_results` は履歴として継続利用する方針で進める。

### 2.3 画面設計

画面側は、DBでロット別現在位置を持ったうえで、進捗管理画面に以下を表示する。

- 注番
- 得意先
- 製品名
- 受注数量
- 納期
- 在庫数
- 引当数
- 残数
- 在庫差引数量
- 各工程のロット別現在数量
- 合計

工程欄は、同一工程に複数ロットがある場合、ロットNoと数量を縦並びで表示する。  
工程欄内でロットを合算しない。

## 3. 仕様確認結果

### 3.1 確定仕様

| 項目 | 確認結果 |
| --- | --- |
| 工程移動単位 | ロット単位 |
| 今日分・翌日分 | 別ロットとして別々に移動・表示 |
| 実績登録後の表示 | 登録数量は次工程に表示し、元工程に残さない |
| 元工程の表示 | 表示対象数量がなければ `-` |
| 工程移動対象 | 生産数量のみ |
| 製造・洗浄 | DB上は別工程、画面上は必要に応じて「製造・洗浄」として表示統合 |
| 超過生産 | 許可し、在庫として扱う |
| 引当・出荷上限 | 受注数量を上限 |
| 計量登録 | 通常運用から廃止 |
| 計量表出力 | 通常運用から廃止 |
| 生産予定部署 | 製造G、品質管理G、梱包出荷G |
| 部署別絞り込み | 部署のみ |

### 3.2 SQL作成前に注意する点

以下はブロッキングではないが、SQL作成時に扱いを間違えると後戻りが大きい。

| No | 論点 | 現状の整理 | 対応方針 |
| --- | --- | --- | --- |
| 1 | 直接編集履歴を既存履歴テーブルに残すか、新規履歴テーブルに残すか | 要件では「既存履歴テーブル」、DB設計では `process_lot_movements` | ロット別現在位置の整合性を保つため、工程移動・直接編集は `process_lot_movements` に集約する方針が実装しやすい |
| 2 | 最終工程完了時の在庫化タイミング | DB設計では「在庫化または完了処理」として保留 | 梱包工程完了時に在庫化するのが現行運用との整合性が高い |
| 3 | 既存データの初期移行 | 既存累計からロット別現在位置を完全復元できない | 新仕様適用後のデータを正とし、既存データは参照継続に留める |
| 4 | `completed_amount` の今後の役割 | 既存画面・ガントで使われる可能性あり | 互換用の累計値として当面維持し、進捗一覧の現在数量には使わない |
| 5 | 計量登録・計量表出力の廃止範囲 | 通常運用から廃止 | 画面導線は外すが、既存データ参照のため即削除はしない |

## 5. 優先順位

| 優先度 | タスク群 | 理由 |
| --- | --- | --- |
| Critical | DB基盤、実績登録RPC、進捗管理表示 | 新仕様の中核。ここがないと後続画面が成立しない |
| High | 直接編集履歴、注番管理履歴、生産予定部署別 | 運用上の追跡性と現場入力に必要 |
| Medium | 在庫・引当・出荷連携の拡張 | 超過生産と出荷制御の精度向上に必要 |
| Low | 廃止導線整理、文言整理 | 中核実装後に安全に反映可能 |

## 6. 現時点の結論

- SQL作成に進める前段階として、要件・システム設計・DB設計の整合性は概ね取れている。
- ブロッキングとなる仕様不明点はない。
- ただし、直接編集履歴の保存先は、要件上の「既存履歴テーブル」とDB設計上の `process_lot_movements` の表現差がある。
- 実装上は、ロット別工程移動履歴を一元管理できる `process_lot_movements` に集約する方が安全。
- SQL作成は、ユーザーから明示的に許可が出るまで行わない。
